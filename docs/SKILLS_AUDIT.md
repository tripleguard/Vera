# Аудит поддержки skills в Vera

Дата: 11 июня 2026 года

## Решение

Поддержку skills в Vera стоит внедрять.

Однако skill должен быть не новым исполняемым инструментом и не большим промптом,
который постоянно передаётся модели. Для Vera оптимальна следующая модель:

- tool выполняет атомарное действие;
- skill описывает проверенную процедуру решения задачи с помощью tools;
- Vera выбирает подходящий skill до основного запроса к LLM;
- в контекст загружается только один наиболее подходящий skill;
- маленькая модель получает короткую, линейную инструкцию;
- крупная модель может выбирать и комбинировать несколько skills;
- сторонний skill по умолчанию не получает право запускать произвольный код.

Это даст заметную пользу и Qwen 3.5 2B, и моделям класса 30B, но режимы их
работы должны различаться.

## Что такое skill

Agent Skill — каталог с обязательным `SKILL.md` и необязательными ресурсами:

```text
skills/
  presentations/
    SKILL.md
    references/
    scripts/
    assets/
```

Стандарт Agent Skills предусматривает YAML frontmatter с `name` и
`description`, а тело файла содержит инструкции. Каталоги `scripts`,
`references` и `assets` являются рекомендуемыми, но не обязательными.

Главный принцип формата — progressive disclosure:

1. При запуске загружаются только имя и краткое описание skill.
2. Полный `SKILL.md` читается лишь после активации.
3. Дополнительные файлы читаются только по необходимости.

Это особенно важно для Vera, потому что её стандартный контекст модели сейчас
ограничен 8192 токенами.

## Текущее состояние Vera

### Сильные стороны

- Уже существует OpenAI-совместимый function calling.
- Инструменты отделены от их JSON-схем.
- Инструментальный цикл ограничен четырьмя итерациями.
- Есть тайм-аут выполнения tools и аудит успешных/неуспешных вызовов.
- Системный промпт собирается из отдельных файлов.
- Есть локальная память с BM25, которую можно переиспользовать для skill routing.
- Есть планировщик и последовательное выполнение составных задач.
- Vera поддерживает локальный llama-server и внешние OpenAI-совместимые серверы.

### Архитектурные проблемы

#### 1. Инструкции к tools дублируются

Описание инструментов находится одновременно в:

- `data/TOOLS.md`;
- `main/tool_definitions.py`;
- эвристиках в `main/agent.py`;
- специальных обработчиках презентаций и поиска.

Текущий `TOOLS.md` занимает около 6167 символов, а полный базовый промпт —
около 8994 символов до добавления памяти, истории и схем tools.

Skill layer позволит убрать процедурные сценарии из постоянного промпта.

#### 2. Все схемы tools обычно передаются сразу

Сейчас модель видит пять function schemas даже тогда, когда запрос относится
только к одному инструменту. При росте количества функций это ухудшит выбор
инструмента, увеличит контекст и станет особенно заметно на моделях 2B–7B.

Skills должны объявлять необходимые tools, а Vera должна передавать модели
только их подмножество.

#### 3. Есть слишком много специальных веток

Поиск, презентации, small talk, прикреплённые файлы и обычный код
маршрутизируются отдельными эвристиками. При добавлении новых возможностей
`agent.py` будет разрастаться.

Skill router сможет перенести выбор сложной процедуры в отдельный слой, не
удаляя надёжные системные команды и быстрые эвристики.

#### 4. Tool loop использует текстовую обратную связь

После выполнения tool Vera формирует новый пользовательский prompt с
результатами. Она не сохраняет полноценную последовательность
`assistant.tool_calls` → `tool` → `assistant`.

Это не блокирует первую версию skills, но перед сложными составными skills
желательно перейти на нативную историю tool calls. Крупные модели лучше
удерживают план и результаты при стандартной структуре сообщений.

#### 5. Code interpreter не является песочницей

`code_interpreter` запускает Python с окружением основного процесса и имеет
доступ к пользовательской файловой системе. Тайм-аут ограничивает время, но не
права.

Поэтому автоматический запуск `scripts/` из скачанного skill сейчас является
критическим риском. В первой версии skills разрешено использовать только
зарегистрированные Vera tools.

## Маленькая модель: Qwen 3.5 2B

### Что ей поможет

- одна короткая процедура вместо длинного общего промпта;
- заранее выбранный ограниченный набор tools;
- пошаговая инструкция без альтернативных ветвей;
- строгие JSON-схемы;
- программная проверка результата после каждого шага;
- детерминированные backend-операции для сложных форматов.

Исследования малых function-calling моделей показывают, что специализированное
обучение и tool retrieval позволяют моделям примерно 1.1B–4B выполнять вызовы
инструментов, но надёжность сильно зависит от числа доступных tools, сложности
схем и качества маршрутизации. TinyAgent отдельно использует tool retrieval,
чтобы не помещать все инструменты в контекст.

### Что ей навредит

- загрузка нескольких длинных skills;
- предложение самой выбрать из десятков похожих процедур;
- вложенные ссылки из одного `SKILL.md` в другой;
- сложные условные алгоритмы;
- разрешение самостоятельно писать и запускать orchestration-код;
- одновременная передача всех tools;
- skill длиной в тысячи токенов.

### Режим Small

Для моделей до условных 7B:

- skill выбирает Vera, а не модель;
- автоматически активируется максимум один skill;
- рекомендуемый размер body: 400–900 токенов;
- жёсткий максимум: 1200 токенов;
- skill содержит не более 6–8 шагов;
- передаются только `required_tools`;
- при неуверенном routing skill не активируется;
- orchestration и проверка выполняются Python-кодом Vera.

## Крупная модель: 30B+

Модель 30B обычно лучше:

- различает похожие skills;
- удерживает длинную процедуру;
- корректирует план после ошибки tool;
- комбинирует поиск, анализ и создание файла;
- работает с несколькими результатами tools;
- выбирает релевантные reference-файлы.

### Режим Large

- router может показать модели top-3 описания skills;
- допускается активация до двух skills;
- лимит одного skill: примерно 2500 токенов;
- разрешён model-assisted routing;
- разрешена адаптация порядка шагов;
- всё равно действуют permission policy и лимиты tool loop;
- автоматическое исполнение непроверенных скриптов остаётся запрещённым.

Размер модели нельзя надёжно определять только по имени файла. Нужна настройка
`skills.model_profile`: `small`, `balanced`, `large` или `auto`, где `auto`
использует имя модели, размер контекста и ручное переопределение.

## Рекомендуемая архитектура

```text
User request
    |
    v
System command router
    |
    v
Skill router (BM25 + triggers + optional LLM rerank)
    |
    v
Skill policy / permissions
    |
    v
Prompt composer + filtered tool schemas
    |
    v
LLM
    |
    v
Existing tool executor
    |
    v
Validator / final response
```

### SkillRegistry

При запуске:

- сканирует built-in и пользовательские каталоги;
- разбирает frontmatter;
- валидирует имя, описание и пути;
- создаёт индекс метаданных;
- не читает полное тело каждого skill;
- отслеживает изменения файлов по mtime.

Рекомендуемые области:

```text
<install>/skills/                   встроенные, только чтение
%LOCALAPPDATA%/Vera/skills/         пользовательские
<workspace>/.vera/skills/           проектные, только после разрешения
```

При конфликте имён приоритет:

```text
project > user > built-in
```

Переопределение встроенного skill должно явно показываться в UI.

### SkillRouter

Для первого релиза не нужен embedding model. В Vera уже есть BM25.

Индексировать следует:

- `name`;
- `description`;
- необязательные `keywords`;
- примеры запросов;
- названия разрешённых tools.

Routing:

1. Явная команда пользователя `/skill presentations` имеет высший приоритет.
2. Точные triggers и системные правила идут следующими.
3. BM25 возвращает top-3 кандидата.
4. Для small-профиля применяется score threshold и margin между первым и
   вторым кандидатом.
5. Для large-профиля LLM может выбрать кандидата из top-3.
6. При низкой уверенности запрос идёт без skill.

Skill не должен активироваться на основании одного общего слова вроде
«создай», «файл» или «найди».

### PromptComposer

Вместо добавления всех skills:

```text
<active_skill name="presentations">
...короткая процедура...
</active_skill>
```

Полный текст skill добавляется после базовых правил безопасности, но до памяти
и пользовательского сообщения. Skill считается инструкцией приложения, а
данные из `references/` — недоверенным контекстом.

### Tool filtering

Skill объявляет tools:

```yaml
allowed-tools: web_search create_presentation read_document
```

Vera вычисляет пересечение:

```text
tools_for_request =
    tools_enabled_by_user
  ∩ tools_allowed_by_policy
  ∩ tools_requested_by_skill
```

Модель никогда не может расширить этот набор текстом из skill.

### Policy

Рекомендуемые capability-классы:

- `read_files`;
- `write_files`;
- `network`;
- `messaging`;
- `execute_code`;
- `system_control`;
- `background_tasks`.

Skill получает capabilities из манифеста, но окончательное решение принимает
Vera. Опасные действия должны требовать подтверждения независимо от текста
skill.

## Предлагаемый формат `SKILL.md`

Следует сохранить совместимость с Agent Skills и хранить расширения Vera в
поле `metadata`.

```yaml
---
name: presentations
description: Создаёт исследованные и визуально разнообразные презентации PPTX.
license: MIT
compatibility: Vera 1.2+
allowed-tools: web_search create_presentation
metadata:
  vera.category: documents
  vera.model-profile: small
  vera.activation: auto
  vera.risk: write-files,network
  vera.version: "1"
---

# Создание презентации

1. Определи тему, аудиторию и желаемое число слайдов.
2. Если интернет доступен, собери факты и сохрани источники.
3. Построй связный план без повторяющихся слайдов.
4. Выбери визуальный стиль по теме, а не фиксированный шаблон.
5. Вызови `create_presentation`.
6. Проверь файл и сообщи путь пользователю.
```

`description` должна описывать и назначение, и ситуации активации. Это
соответствует рекомендациям Agent Skills.

## Какие skills нужны Vera первыми

### 1. presentations

Лучший первый кандидат, потому что процедура уже существует в виде
специальной ветки.

Skill должен описывать:

- исследование;
- проверку источников;
- построение истории;
- выбор стиля;
- разнообразие layout;
- генерацию;
- техническую валидацию PPTX.

Само создание файла остаётся детерминированным Python tool.

### 2. document-report

Поиск или обработка приложенных материалов → структура → DOCX/MD → проверка.

### 3. spreadsheet-analysis

Чтение таблицы → определение колонок → расчёты → выводы → новый XLSX.

### 4. web-research

Несколько поисковых запросов → удаление дублей → оценка источников → синтез
с указанием ссылок.

### 5. code-review

Чтение файлов → поиск дефектов → сортировка по серьёзности → ссылки на файлы.
На первом этапе без автоматического изменения или запуска кода.

Telegram, управление громкостью, запуск приложений и простые системные команды
не следует превращать в skills. Это атомарные tools/commands.

## Что не следует делать

- Не добавлять весь каталог skills в системный prompt.
- Не превращать каждый tool в skill.
- Не позволять модели 2B самостоятельно выбирать из большого marketplace.
- Не запускать `scripts/` напрямую через текущий `code_interpreter`.
- Не устанавливать skills из интернета без просмотра манифеста и разрешений.
- Не считать Markdown доверенным кодом.
- Не разрешать skill менять системный prompt, policy или список permissions.
- Не смешивать долговременную память пользователя и инструкции skill.
- Не делать автоматическую композицию skills обязательной.

## План внедрения

### Этап 0. Бенчмарк

Собрать 60–100 запросов:

- обычный чат;
- неоднозначные запросы;
- презентации;
- исследования;
- документы;
- ошибочные и опасные команды.

Измерять:

- accuracy выбора skill;
- false activation rate;
- успешность tool calls;
- валидность аргументов;
- итоговую успешность задачи;
- токены и время;
- количество подтверждений;
- различия между Qwen 3.5 2B и тестовой 30B.

### Этап 1. Read-only skills

- `SkillRegistry`;
- парсер frontmatter;
- BM25-индекс;
- активация одного skill;
- лимиты размера;
- только built-in skills;
- без `scripts/`;
- логирование `skill.selected`, `skill.loaded`, `skill.rejected`.

### Этап 2. Tool filtering

- добавить `allowed-tools`;
- выбирать schemas динамически;
- удалить подробные процедуры из постоянного `TOOLS.md`;
- оставить в `TOOLS.md` только общие правила безопасности и поведения.

### Этап 3. Первый production skill

Перенести orchestration презентаций в `presentations/SKILL.md`, сохранив
детерминированный генератор и существующий offline fallback.

Важно сначала запускать старый и новый pipeline параллельно на бенчмарке, а не
удалять текущий путь сразу.

### Этап 4. Пользовательские skills

- импорт локального каталога или ZIP;
- экран просмотра инструкций и permissions;
- enable/disable;
- ручной режим активации;
- журнал происхождения и версии;
- запрет symlink/path traversal.

### Этап 5. Скрипты

Только после появления отдельного sandbox runner:

- отдельный процесс;
- минимальное окружение;
- рабочий каталог skill;
- deny-by-default сеть;
- allowlist файловых путей;
- ограничение CPU, памяти, времени и вывода;
- подтверждение записи/сети/системных действий.

### Этап 6. Large-model orchestration

- model-assisted routing по top-3;
- максимум два активных skill;
- нативная история tool messages;
- продолжение после частичной ошибки;
- отдельные лимиты контекста и шагов.

## Критерии готовности

Skills можно включать по умолчанию для 2B, если на бенчмарке:

- routing accuracy не ниже 90%;
- false activation rate не выше 3%;
- успешность целевых задач выше baseline минимум на 10 процентных пунктов;
- обычный чат не становится заметно медленнее;
- средний дополнительный контекст не превышает 900 токенов;
- нет исполнения неразрешённых capabilities.

Для 30B дополнительно измерять качество композиции двух skills и восстановление
после ошибки tool.

## Итоговая рекомендация

Vera уже переросла архитектуру, где все процедуры удобно хранить в одном
`TOOLS.md` и в специальных `if`-ветках. Skills являются логичным следующим
слоем, потому что позволят:

- масштабировать число сценариев;
- сократить постоянный prompt;
- улучшить сложные задачи;
- сохранить локальность и offline-режим;
- дать продвинутым пользователям расширяемость;
- использовать более сильные 30B-модели без ограничения возможностями
  встроенной 2B-модели.

Но главная ценность появится не от самого формата `SKILL.md`, а от качественного
router, фильтрации tools, permission policy, валидации результатов и разных
профилей для малых и крупных моделей.

Рекомендуемый старт: этапы 0–3, один встроенный skill `presentations`, без
исполнения сторонних scripts.
